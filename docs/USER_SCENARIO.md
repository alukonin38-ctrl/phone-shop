# Сценарий пользователя: магазин телефонов

Документ описывает, как пользователь взаимодействует с системой «Магазин телефонов»
(регистрация, вход, каталог) и что система должна отвечать — в том числе в ошибочных ситуациях.

Автоматическая проверка этого сценария: `cd server && npm run scenario`.
Ручная проверка в браузере: см. «Как воспроизвести вручную» в конце файла.

## 1. Участники и предусловия

| Пункт | Значение |
|---|---|
| Пользователь | новый посетитель сайта (без аккаунта) |
| Что нужно | сервер запущен (`cd server && npm start`), открыт `index.html` |
| Адрес API | `http://localhost:5000/api` (задан в `main.js`) |
| База данных | SQLite-файл `server/users.db` |

## 2. Основной сценарий (Happy path)

| № | Действие пользователя | Что делает система | Ожидаемый результат |
|---|---|---|---|
| 1 | Открывает страницу магазина | Фронтенд загружает каталог, проверяет сохранённую сессию | Видна форма «Вход / Регистрация» |
| 2 | Вкладка «Регистрация», вводит логин `ivan_2025`, пароль `ScenarioPass123` (повторяет тот же) | `POST /api/register` → проверка логина, проверка пароля по списку 100k частых паролей и детектору «клавиатурного мусора» → Argon2id → запись в SQLite | `201` «Регистрация успешна»; пароль хранится как `$argon2id$...`, никогда — в открытом виде |
| 3 | Вкладка «Вход», вводит тот же логин и пароль | `POST /api/login`: проверка блокировки, поиск пользователя, `argon2.verify`, сброс счётчика неудачных попыток | `200` «Вход выполнен», в каталоге видно «Вы вошли как ivan_2025» |
| 4 | Листает каталог телефонов | Фронтенд сортирует и рисует карточки | 16 карточек с ценой в формате «79 990 ₽» |
| 5 | Нажимает «Выйти» | Фронтенд очищает `sessionStorage` | Снова видна форма входа, поля очищены |

## 3. Альтернативные сценарии (Negative path)

| № | Действие пользователя | Что делает система | Ожидаемый результат |
|---|---|---|---|
| 3.1 | Регистрируется с паролем `password123` | Проверка по списку частых паролей | `400`, «Пароль слишком распространён. Придумайте другой.» |
| 3.2 | Регистрируется с логином `пользователь` | Логин допускает только латиницу, цифры, `_`, `-` | `400` «Логин может содержать только латиницу, цифры, "_" и "-"» |
| 3.3 | Регистрируется с логином `ab` | Ограничение длины 3–20 символов | `400` «Логин должен быть не короче 3 символов» |
| 3.4 | Вводит разные пароль и подтверждение | Сравнение `password` и `confirm` | `400` «Пароли не совпадают» |
| 3.5 | Регистрируется с логином, который уже занят | Проверка уникальности в БД | `400` «Пользователь уже существует» |
| 3.6 | Входит с неверным паролем (1-я ошибка) | Увеличивает счётчик неудачных попыток, ставит блокировку | `401` «Неверный логин или пароль. Подождите 5 с.» — на кнопке идёт обратный отсчёт |
| 3.7 | Сразу пробует войти снова (даже с верным паролем) | Проверка блокировки до всех остальных действий | `429` «Слишком много попыток. Повторите через N с.» |
| 3.8 | Ошибается второй раз после окончания задержки | Счётчик = 2, задержка растёт | `401`, задержка 10 секунд |
| 3.9 | Ошибается третий раз | Счётчик ≥ 3 | `401`, задержка 15 секунд (дальше не растёт) |
| 3.10 | Наконец вводит верный пароль после задержки | Успешный вход сбрасывает счётчик (`login_attempts` очищается) | `200`, следующая ошибка снова даёт задержку 5 с |
| 3.11 | Входит с логином, которого нет | Чтобы не подсказывать злоумышленнику, сообщение такое же, как для неверного пароля | `401` «Неверный логин или пароль…» |
| 3.12 | Открывает страницу, когда сервер не запущен | Запрос падает | Сообщение «⚠️ Сервер недоступен. Проверьте, запущен ли backend.» |
| 3.13 | Другой пользователь входит, пока первый заблокирован | Блокировка хранится по логину | Второй пользователь входит нормально (`200`) |

## 4. Критерии приёмки

1. Пароли **никогда** не хранятся и не логируются в открытом виде — только Argon2id-хеш.
2. Неудачные попытки входа приводят к задержкам 5 → 10 → 15 секунд (счётчик обнуляется после успешного входа).
3. Сообщение об ошибке входа одинаково для «нет такого логина» и «неверный пароль».
4. Регистрация невозможна без прохождения проверок логина и пароля.
5. Все ответы API — JSON; коды: `201` создание, `200` успех, `400` ошибка данных, `401` неверные данные, `429` блокировка, `500` внутренняя ошибка.

## 5. Как это проверяется автоматически

| Сценарий | Тест |
|---|---|
| 2.2–2.3 регистрация и вход | `server/__tests__/api.test.js` → `Happy path` |
| 2.5 выход, 3.12 недоступный сервер | проверяется вручную (только фронтенд) |
| 3.1–3.5 ошибки ввода | `api.test.js` → `POST /api/register — Negative path`, `validators.test.js` |
| 3.6–3.11 задержки и блокировки | `api.test.js` → `POST /api/login — блокировка`, `rateLimiter.test.js` |
| 3.13 блокировка на пользователя | `rateLimiter.test.js` → «попытки разных пользователей не смешиваются» |
| хеширование Argon2id | `hashService.test.js` |

Команды: `npm test` (все тесты), `npm run scenario` (сценарий целиком), `npm run bench` (стоимость хеширования).

## 6. Как воспроизвести вручную в браузере

```powershell
# консоль 1 — сервер
cd server
npm start

# консоль 2 — статический сервер для фронтенда
cd ..
npx http-server . -p 5501
# либо:  python -m http.server 5501
```

Откройте `http://localhost:5501`, зарегистрируйтесь и повторите шаги из таблиц выше.
Проверить данные напрямую можно так: `sqlite3 server/users.db "select login, substr(password_hash,1,30) from users;"`
(или любым SQLite-клиентом) — в колонке `password_hash` должен быть `$argon2id$...`.
